## 2. Design

| Piece | Detail |
| --- | --- |
| Templates | Table `notification_templates` (seeded in Flyway **V27**) |
| Delivery log | `notification_deliveries` — status `PENDING` / `SENT` / `FAILED` / `SKIPPED`, `attempt_count`, `last_error`, `next_retry_at` |
| Channel port | `NotificationChannelSender` — `logging` (default) or `smtp` (`JavaMailSender`) |
| Triggers | Domain events after commit from admissions approve + finance collect payment |
| Retry | `NotificationRetryJob` polls due `PENDING` rows; exponential backoff (`initial-retry-seconds` × `backoff-multiplier^n`) |

Callers never touch notification persistence (ArchUnit).

---

## 3. Configuration

```yaml
ims:
  notification:
    enabled: true
    channel: logging   # or smtp
    from: noreply@ims.local
    max-attempts: 5
    initial-retry-seconds: 30
    backoff-multiplier: 2.0
    retry-poll-ms: 15000

# When channel=smtp:
spring:
  mail:
    host: localhost
    port: 1025
```

---

## 4. How to verify locally

1. Start API with `ims.notification.channel=logging` (default).
2. Approve an admission that has an applicant email → log line `Notification email sink` + row `SENT` in `notification_deliveries`.
3. Collect a payment for a student with email → second `SENT` delivery.
4. Or run: `mvn -pl ims-api -am test -Dtest=NotificationEmailIT -Dsurefire.failIfNoSpecifiedTests=false`

Optional triggers (fee overdue, result published) remain out of MVP scope per Step 7.6.
